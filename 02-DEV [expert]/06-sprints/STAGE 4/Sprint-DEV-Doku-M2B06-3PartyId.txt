2. KONZEPT UND ENTSCHEIDUNGEN
--------------------------------------------------------------------------------

2.1 Was ist die 3PartyId?
--------------------------
Die 3PartyId ist EINE Property pro BusinessProcess-Element in Archi.
Sie enthält immer die BPMN Process ID des zugehörigen BPMN-Prozesses.

Zwei Fälle:

  Fall A — Prozess aus Archi heraus entstanden (Normalfall):
    BPMN Process ID == Archi Identifier
    → 3PartyId = Archi ID
    → Beide Werte sind identisch — das ist korrekt und gewollt

  Fall B — Prozess extern in Camunda erstellt (3rd Party):
    BPMN Process ID ist eine Camunda-generierte ID (z.B. Process_0ux338x)
    → 3PartyId = diese Camunda-ID
    → Archi-ID und 3PartyId sind unterschiedlich

  Entscheidung: Nur eine Property "3PartyId" — keine separate "BPMN_ID".
  Die 3PartyId IST die BPMN Process ID, immer, in beiden Fällen.

2.2 Property-Definition (Standard)
------------------------------------
  PropertyDefinition identifier : propid-3partyid
  PropertyDefinition name       : 3PartyId
  Property key                  : 3PartyId
  Scope                         : BusinessProcess Elemente mit sourceSystem=archi

2.3 Matching-Logik in M2B06
-----------------------------
  Primär  : BPMN Process ID == Archi identifier (direkter ID-Match)
  Fallback : BPMN Process Name == Archi element name (Name-Match)
  Kein Match → Element wird übersprungen, Warnung im Log

2.4 Bekanntes Import-Muster (dokumentiert)
-------------------------------------------
  Beim ersten Archi CSV-Import nach einem vollständigen Run kann es zu
  einem Fehler kommen wenn properties.csv und relations.csv im Import-
  Ordner noch Reste des vorherigen Runs enthalten.

  Lösung (bekannt und getestet):
  1. Ersten Run durchführen → Import schlägt fehl
  2. properties.csv + relations.csv im Import-Ordner löschen
  3. Run nochmals durchführen → Import erfolgreich

  Ursache: Archi CSV-Import verarbeitet properties.csv und relations.csv
  beim ersten Import und hinterlässt Reste wenn der Run unterbrochen wird.

6. LESSONS LEARNED
--------------------------------------------------------------------------------

  - Kontext-Overhead: Bei langen Sessions mit vielen Entwicklungsschleifen
    können alte PropertyDefinitions und Zwischenstände in master.xml
    akkumulieren. Vor dem Schreiben neuer Properties immer prüfen ob
    bereits PropertyDefinitions mit ähnlichem Zweck existieren.

  - Diagnose-First: Das erstellte M2B06-diagnose.py hat den Altlast-
    Befund (3 veraltete PropertyDefinitions) zuverlässig aufgedeckt.
    Diagnose-Scripts vor Fix-Scripts ist bewährtes Muster.

  - Sauberer Reset: master.xml + CSV Masters löschen und vollständigen
    Run neu starten ist der zuverlässigste Weg um Akkumulationsfehler
    zu beheben. Schneller als chirurgische Einzelkorrekturen.
